## 1. 지금 어디까지 닫혀 있나

```
① learn                                        ② review
   통계 경로  ─ 이름 세기 → AI 판정 → 게이트        내장 검사 (AI 없음)
   추론 경로  ─ 구조 요약 → 훑기(싼) → 정독(강한)     · 이름 규칙
                → 리포 전체에 측정 → 게이트          · 구조 규칙 6종 + query
                                                    LLM triage (진단·추가 결함)
```

**검사 어휘**: `naming` `header_directive` `include_direction` `return_type`
`member_ownership` `base_class` + **`query`**(AI가 직접 씀).
`query` 가 생긴 뒤로는 새 종류를 위해 코드를 고칠 일이 원칙적으로 없습니다.

## 2. 할 일 — 순서대로

### ⑴ 벤더 코드 배제 ★ 먼저

**근거(실측):** 전부 읽기(`--infer-all`)를 돌렸더니 12묶음 중 5개가 벤더 파일 하나
(`src/contrib/dragonbox.h`, 243 KB)였고, 관찰의 상당수가 **남의 코드 관행**이었다
(`JKJ_` 매크로 규칙 등). 폴더 이름 목록(`third_party`, `vendor`…)이 `src/contrib` 를 못 거른다.

**할 일 (확실한 것부터):**
1. `.gitmodules` — 서브모듈은 문자 그대로 남의 코드. **추측이 아니라 사실**
2. `git log` — 커밋 하나로 통째로 들어온 디렉터리
3. 이름 분포 이상치 — 어떤 폴더가 나머지와 판이하게 다르면 외부 코드

- 고칠 곳: `conventions/extractor.py`(`select_files`), `config.py`
- 확인: yaml-cpp 에서 `src/contrib` 가 빠지는지, 전부 읽기 묶음이 12 → 7 로 주는지

### ⑵ 질의 성공률 올리기

**근거(실측):** 재시도는 만들었는데 복구율이 **15건 중 3건(20%)** 이다. 미검증이 19 → 12 로 줄었을
뿐 대부분은 여전히 못 잰다.

**할 일:** 실패 유형별로 다른 힌트를 주거나(컴파일 오류 vs 조건 0건), 프롬프트의 검증된 예시를
늘리기. 어느 쪽이 듣는지는 `검사 고쳐쓰기` 집계로 본다.

- 고칠 곳: `conventions/proposer.py` (`_REPAIR_SYSTEM`, `_INFER_SYSTEM`)
- **재시도는 1회 유지.** 무한 루프로 토큰 태우지 않기

### ⑶ `--infer-all` 은 ⑴⑵ 다음에 켠다

기능은 완성돼 있다 — 97개 파일 → 12묶음, **583,391자 100% 커버**, 보내기 전 규모 고지, 큰 파일은
줄 단위 분할. 하지만 지금 켜면 결과가 더 나쁘다:

| | 읽은 양 | 검증된 규칙 |
|---|---|---|
| 6개 파일, 강한 모델 | 6% | **3개** |
| 97개 파일, 싼 모델 | 100% | 0개 (검사를 아예 안 씀) |
| 97개 파일, 강한 모델 | 100% | 1개 (질의 대부분 실패) |

**많이 읽는 게 목적이 아니라 잴 수 있는 걸 얻는 게 목적**이다. ⑴⑵가 되면 그때 다시 잰다.

### ⑷ 구조 요약이 보여주는 축 넓히기

**근거(실측):** yaml-cpp 실행에서 `query` 사용 **0건**. 이유가 구조적입니다 —
**구조 요약이 담는 것과 내장 지름길이 같은 열거**라서, 훑기가 짚어주는 곳은 항상 지름길로 덮입니다.

지금 요약에 없는데 함수 몸통 밖에 있는 것들 (yaml-cpp 기준):

```
function_declarator  1638      const     1409      template  392
alias_declaration     200      namespace  157      access_specifier  86
override               49      enum        47      virtual   42
```

**할 일:** 요약에 수식어 분포(const/override/static), 네임스페이스 배치, 접근 지정자 순서를 추가.

- 고칠 곳: `conventions/survey.py` (`ClassSummary`, `render`)
- 상한 주의: 요약이 커지면 2단 여과의 근거(싼 1차는 싸다)가 사라집니다. 지금 4,467자 → **1만자 넘기지 말기**
- 확인: 훑기가 수식어 쪽을 짚는지, `query` 사용률이 오르는지

### (완료) 전체 코드를 묶어서 읽기 — ⑶ 참고

**근거:** 150,300 토큰 = 싼 모델 $0.023 ≈ **지금 6개 파일 읽는 값과 같습니다.**
6개가 아니라 97개를 다 봅니다.

**⑴ 이 먼저 되어야 합니다.** 묶음별 관찰을 **말로 합치려면** AI를 또 불러야 하고, 그러면
"몇 묶음에서 봤나"가 AI 의견이 됩니다(심판이 선수). 관찰마다 질의가 붙어 있으면 **각각을 리포
전체에 재보면 되니 합칠 필요가 없습니다** — 같은 걸 재면 같은 숫자로 수렴합니다.

- 설계: 묶음마다 싼 모델 → 관찰 + 질의 → 코드가 전부 측정 → 게이트가 정리
- 고칠 곳: `conventions/proposer.py`
- **반드시**: 별도 opt-in 플래그. 리포 전체 코드가 외부로 나갑니다. 돌리기 전에
  *"파일 N개 / 약 M 토큰 / 예상 $X 를 외부로 보냅니다"* 를 보여주고 확인받기
- 규모 참고: 5,000개 파일 ≈ 7.7M tok ≈ $1.16 (싼 모델). 비용은 문제가 아니고 **시간·병렬 호출**이 문제

### (⑴로 승격) 벤더링된 폴더 판별

**근거:** 지금은 제가 적은 이름 목록(`third_party`, `vendor`, `deps`…)입니다. fmt 에서 이 목록이
`test/gtest/` 를 못 걸러서 **UpperCamel 2,845개 중 2,837개가 번들 googletest 것**이었고,
snake_case 리포가 63% UpperCamel 로 보였습니다.

**할 일 (확실한 것부터):**
1. `.gitmodules` — 서브모듈은 문자 그대로 남의 코드. **추측이 아니라 사실**
2. `git log` — 커밋 하나로 통째로 들어온 디렉터리
3. 이름 분포 이상치 — 어떤 폴더가 나머지와 판이하게 다르면 외부 코드
   (쪼개짐 감지가 카테고리 단위로 이미 하는 일과 같은 원리)

- 고칠 곳: `conventions/extractor.py` (`select_files`), `config.py`
- 못 없애는 추측은 **보이게** 두기: 폴더별 식별자 수 로그가 fmt gtest 를 잡은 방법입니다

### ⑸ 분류 못 한 선언을 세서 보고

**근거:** 카테고리가 5개뿐이라 enum 47 / namespace 157 / typedef 205 가 **조용히 무시**됩니다.
그러면 enum 이름 규칙, 네임스페이스 규칙은 있어도 못 찾습니다.

**할 일:** "우리가 어떤 카테고리에도 넣지 못한 선언 N개" 를 세서 learn 출력과
`learn-report.yml` 에 남기기. 판정 못 한 class 선언을 센 것과 **똑같은 모양**입니다.

- 고칠 곳: `languages/cpp/ast.py` (`ScanHealth`), `conventions/extractor.py`
- 효과: 카테고리 목록이 좁다는 사실이 **숫자로** 보입니다

### ⑹ 남은 자잘한 것

| | 내용 |
|---|---|
| `header_directive` 리뷰 검사 | 학습·검증은 되는데 리뷰 적용이 LLM 판단(참고용). 다른 구조 check 처럼 결정적 체커 붙이기 |

## 3. 손대기 전에 알아야 하는 원칙

이 네 개는 여러 번 다시 발견한 것들입니다. 새 코드에도 그대로 적용됩니다.

**① 분모를 먼저 정한다.** 측정 버그는 전부 분모가 주장보다 넓었던 경우였습니다 —
casing 을 casing 신호 없는 이름까지, 소유권을 포인터 아닌 멤버까지, 계층을 레포 전체로.
`query` 가 모집단을 필수 칸으로 만든 이유가 이겁니다.

**② 조용히 넘어가지 않는다.** 결과가 달라지는 저하는 반드시 말합니다.
tree-sitter 폴백, 커버리지 공백, 판정 못 한 class 선언 — 전부 이 원칙으로 고쳤습니다.

**③ 경고는 항상 의미가 있어야 한다.** 그래서 통계에 영향 주는 것(판정 못 한 class 선언)에만
경고하고, 영향 없는 것(템플릿 문법 한계 76곳)은 숫자로만 남깁니다. 항상 켜진 경고는 아무도
안 읽어서 정작 중요한 하나를 묻습니다.

**④ 개수를 비교하지 말고 무엇이 바뀌었는지 본다.** 매크로 전체 치환 때 `public_field` 93 → 66 이
데이터 손실처럼 보였는데, 사라진 것을 하나씩 확인해 보니 `override`(키워드), `string FpToString`
(반환 타입이 붙은 이름) 같은 쓰레기였습니다. 총합만 봤으면 판단이 반대로 갔습니다.

**그리고 게이트는 건드리지 않습니다.** 규칙이 어디서 왔든(통계·AI·손) 코드가 측정하고
사람이 승인합니다. 제안하는 쪽은 얼마든 헐렁하게 열어도 되지만, 이 문은 그대로 둡니다.

## 4. 두 대로 나눠 작업할 때

파일이 겹치지 않게 자르면 이렇게 됩니다.

| | 담당 | 주로 고치는 파일 |
|---|---|---|
| **A** | ⑴ 질의 재시도 + ⑹ `header_directive` 리뷰 검사 | `proposer.py`, `verifier.py`, `checker.py`, `query.py` |
| **B** | ⑵ 요약 확장 + ⑸ 분류 못 한 선언 세기 | `survey.py`, `extractor.py`, `ast.py` |

- 겹칠 위험: `config.py`(상수 추가), `cli.py`(출력 한 줄), 문서. **작게, 자주 커밋**하면 충돌이
  나도 붙이기 쉽습니다.
- ⑶ 전체 읽기는 **⑴ 이 끝난 뒤에** 시작합니다. 그 전엔 관찰을 합칠 방법이 없습니다.
- 문서는 각자 자기 항목만 고치기. `design-history.md` 는 append 성격이라 충돌이 잘 납니다.
